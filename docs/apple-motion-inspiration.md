# Apple motion inspiration for the Susurro voice dictation pill

Research for the 364x64 Linux overlay pill. Date 2026-09-30.

Scope note. This file covers how Apple achieves its UI animation feel across iOS and macOS: spring physics and named presets, easing curves, duration budgets, interruptible and retargetable animation, Dynamic Island expansion mechanics, SF Symbols animation, reduced motion handling, ProMotion behavior, and the governing principles. Each factual paragraph cites its primary source inline, meaning Apple Human Interface Guidelines, Apple developer documentation, or a WWDC session reference. Web equivalents for our Tauri/React pill are marked [First party] when they restate Apple values and [Inferred] when they translate Apple values into CSS or Web Animations API terms. No source code was changed for this research.

Legend. [First party] means Apple HIG, Apple developer documentation, or WWDC session content. [Inferred] means a web equivalent derived by the author for the Tauri/React pill, not published by Apple.

## 1. Governing principles

### 1.1 Direct manipulation and response

Apple's fluid interface model starts from response. People notice latency fast, and even small delays break the feeling that the interface extends the hand, so every interaction including taps and presses must respond instantly and designers must watch for timers that let delays seep back in (Source: https://developer.apple.com/videos/play/wwdc2018/803/). The HIG carries the same rule into static text. It asks for realistic feedback motion that follows gestures and expectations, gives the example that a view revealed by sliding down from the top should not dismiss by sliding sideways, and warns that feedback motion that makes no sense causes disorientation (Source: https://developer.apple.com/design/human-interface-guidelines/motion).

### 1.2 Redirectable and interruptible motion

Apple treats redirection as a first class requirement, not polish. The iPhone X home, multitasking, and app switch gestures form one multi axis gestural space, so a user can head home, peek at multitasking mid gesture, layer a second gesture on top, or interrupt an app launch and send it back, with thought and gesture happening in parallel instead of think then act (Source: https://developer.apple.com/videos/play/wwdc2018/803/). The same talk extends interruption to motion changes mid interaction, using the multitasking pause gesture as the example: Apple detects the change from finger acceleration rather than a velocity timer because waiting for velocity to settle feels too slow (Source: https://developer.apple.com/videos/play/wwdc2018/803/). The HIG states the shipping rule directly. Let people cancel motion instead of making them wait for an animation to finish, especially for animations they will see more than once (Source: https://developer.apple.com/design/human-interface-guidelines/motion).

### 1.3 Continuity and spatial stability

Apple keeps the same UI elements on screen across a transition so the user can track where things went. The iOS 18 zoom transition morphs the tapped cell into the incoming view and stays continuously interactive, so the user can grab and drag it from the start or mid transition (Source: https://developer.apple.com/videos/play/wwdc2024/10145/). For Dynamic Island layouts the HIG demands the same stability across sizes. The expanded presentation must read as an enlarged version of the compact or minimal presentation, with relative placement of elements preserved so expansion looks predictable (Source: https://developer.apple.com/design/human-interface-guidelines/live-activities). The WWDC design talk phrases it as coherence between the two views: keep content in the same relative position when the Island grows (Source: https://developer.apple.com/videos/play/wwdc2023/10194/).

### 1.4 Motion with restraint

The HIG motion page sets four restraints that govern everything else in this file. Add motion purposefully and never as decoration, never use motion as the only channel for important information, avoid adding motion to interactions that repeat frequently since the system already animates standard elements subtly, and favor brief precise feedback because short animations tied to a successful action inform without distracting (Source: https://developer.apple.com/design/human-interface-guidelines/motion). Games get one extra numeric rule. Holding 30 to 60 fps by default on each supported platform counts as smooth, and games should offer power mode switches rather than forcing users into settings first (Source: https://developer.apple.com/design/human-interface-guidelines/motion).

## 2. Spring physics parameters and named presets

### 2.1 Mass, stiffness, damping

Apple models spring motion as an object on a spring defined by three physical properties. Mass is the object's inertia or unwillingness to start and stop moving, stiffness is the force pulling the current value toward the target, and damping is the friction braking the object over time (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). The same three properties appear across frameworks. `CASpringAnimation` exposes mass, stiffness, damping, and initial velocity, with a documented default stiffness of 100 and the rule that raising stiffness cuts oscillations and settling time while lowering it adds oscillations and time (Sources: https://developer.apple.com/documentation/quartzcore/caspringanimation/stiffness and https://developer.apple.com/documentation/quartzcore/caspringanimation). The older UIKit spring API compresses the model to two controls. `dampingRatio` 1.0 decelerates smoothly with no oscillation and values closer to zero add oscillation, while `initialSpringVelocity` should match the view's pre animation velocity for a smooth handoff (Source: https://developer.apple.com/documentation/uikit/uiview/animate(withduration:delay:usingspringwithdamping:initialspringvelocity:options:animations:completion:)).

### 2.2 Duration plus bounce, the design friendly parameters

Apple states that mass, stiffness, and damping are a poor design interface because no real object exists on screen, so it adopted duration plus bounce universally across design and engineering (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). Duration is perceptual, meaning it stays predictable as other parameters change, while settling duration (when the spring is finished enough to remove) varies with many factors and must never gate user facing changes; SwiftUI completion handlers therefore fire on perceptual duration (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). Bounce runs from -1.0 to 1.0. Positive values overshoot (underdamped), 0 gives a smooth critically damped curve with a long tail, and negative values give a flattened overdamped approach (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). The API reference confirms the contract. `spring(duration:bounce:blendDuration:)` defaults to duration 0.5 and bounce 0.0, and for very bouncy springs the duration reads as the oscillation period rather than settling time (Source: https://developer.apple.com/documentation/swiftui/animation/spring(duration:bounce:blendduration:)).

### 2.3 Named presets and their exact numbers [First party]

SwiftUI ships three presets, each defaulting to duration 0.5 and each tunable through duration plus extra bounce (Sources: https://developer.apple.com/documentation/swiftui/spring/smooth(duration:extrabounce/), https://developer.apple.com/documentation/swiftui/spring/snappy(duration:extrabounce/), and https://developer.apple.com/documentation/swiftui/spring/bouncy(duration:extrabounce/)). The base bounce values are 0 for smooth, 0.15 for snappy, and 0.3 for bouncy (Sources: https://developer.apple.com/documentation/swiftui/spring/smooth(duration:extrabounce/), https://developer.apple.com/documentation/swiftui/spring/snappy(duration:extrabounce/), and https://developer.apple.com/documentation/swiftui/spring/bouncy(duration:extrabounce/)). The same three exist as `Animation` values `.smooth`, `.snappy`, and `.bouncy` with matching defaults (Source: https://developer.apple.com/documentation/swiftui/animation/smooth(duration:extrabounce/)). Since iOS 17 a smooth spring is the default for a bare `withAnimation` call (Source: https://developer.apple.com/videos/play/wwdc2023/10156/). UIKit and Core Animation accept the same duration plus bounce parameters (`UIView.animate(duration:bounce:)` and `CASpringAnimation(perceptualDuration:bounce:)`), so one spring spec now travels across all three frameworks (Source: https://developer.apple.com/videos/play/wwdc2023/10158/).

### 2.4 Conversion equations [First party]

WWDC23 publishes the exact conversion from bounce plus duration to physical parameters, with mass fixed at 1 (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). Stiffness equals (2 pi / duration) squared. Damping equals 1 minus 4 pi times bounce / duration when bounce is zero or positive, and 4 pi / (duration plus 4 pi times bounce) when bounce is negative. The `Spring` model type in SwiftUI performs the same conversion in code and exposes mass, stiffness, and damping properties plus `value(target:time:)` and `velocity(target:time:)` evaluators for custom simulations (Source: https://developer.apple.com/videos/play/wwdc2023/10158/).

### 2.5 Choosing bounce, with Apple's own thresholds [First party]

Apple's tuning guidance starts with duration for pacing, then adds bounce for character (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). Bounce 0 is the default choice and the most versatile. Around 0.15 the tail feels brisker without reading as bouncy. Around 0.3 the bounciness becomes noticeable. Above roughly 0.4 motion risks feeling exaggerated for UI elements (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). Bounce suits playful character and physical moments such as the end of a gesture, and the talk warns to keep the choice consistent with whether the app feels serious or playful, relaxed or fast paced (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). The older fluid interfaces talk states the bounciness rule even more narrowly. Reward momentum with overshoot only when the driving gesture itself has momentum (Source: https://developer.apple.com/videos/play/wwdc2018/803/).

## 3. Easing curves and when each applies

### 3.1 The four UIKit curves [First party]

`UIView.AnimationCurve` defines four behaviors. Ease in ease out begins slowly, accelerates through the middle, and slows before completing, and it is the default for most animations. Ease in begins slowly then speeds up. Ease out begins quickly then slows down. Linear runs evenly across its duration (Source: https://developer.apple.com/documentation/uikit/uiview/animationcurve). The block API `animate(withDuration:animations:)` hard codes `curveEaseInOut` with no transition (Source: https://developer.apple.com/documentation/uikit/uiview/animate(withduration:animations:)).

### 3.2 Exact control points [First party, one curve; rest inferred from headers]

Apple publishes exact Bezier control points for one predefined Core Animation curve. Ease in ease out uses control points (0.42, 0.0) and (0.58, 1.0) (Source: https://developer.apple.com/documentation/quartzcore/camediatimingfunctionname/easeineaseout). The `CAMediaTimingFunction` reference confirms the general scheme: curves run from (0,0) to (1,1) with two caller supplied control points, and predefined names cover linear, ease in, ease out, ease in ease out, and default (Source: https://developer.apple.com/documentation/quartzcore/camediatimingfunction). Apple prose does not print the remaining three point sets, so treat widely mirrored header values (ease in (0.42, 0)/(1, 1), ease out (0, 0)/(0.58, 1), linear (0, 0)/(1, 1), default (0.25, 0.1)/(0.25, 1)) as [Inferred] rather than first party. SwiftUI's `timingCurve(p1x:p1y:p2x:p2y:duration:)` takes the same two control points with a default duration of 0.35 seconds (Source: https://developer.apple.com/documentation/swiftui/animation/timingcurve(_:_:_:_:duration:)).

### 3.3 When Apple reaches for springs instead of curves [First party]

The springs session compares continuities directly. Ease in out and springs both offer continuous position and velocity from rest, but only springs preserve continuity when an initial velocity exists, whether that velocity comes from a gesture handoff or from retargeting an unfinished animation to a new destination (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). SwiftUI therefore recommends springs as the general choice because they feel organic, preserve velocity, and come to rest naturally (Source: https://developer.apple.com/videos/play/wwdc2023/10156/). Timing curves keep one role: predefined multi step sequences. Keyframe tracks explicitly use linear, spring, cubic, and jump (`MoveKeyframe`) interpolation between fixed keyframes, and Apple warns that keyframes cannot retarget gracefully mid flight, so they suit event driven or looping animations rather than interactive state changes (Source: https://developer.apple.com/videos/play/wwdc2023/10157/).

### 3.4 Web equivalents for the pill [Inferred]

Map ease out to `cubic-bezier(0, 0, 0.58, 1)` and ease in ease out to `cubic-bezier(0.42, 0, 0.58, 1)`, using the one Apple published point set and header mirrored values for the rest. In the Web Animations API these become `easing: "cubic-bezier(0, 0, 0.58, 1)"` and `easing: "cubic-bezier(0.42, 0, 0.58, 1)"`. Reserve true spring motion for state changes that can be interrupted (pill show, hide, state morphs) and implement it with a spring solver in JavaScript or a motion library, since a fixed cubic Bezier cannot preserve incoming velocity the way section 2 springs do. Keep keyframe style multi step sequences for one shot event pulses only, never for the interruptible pill frame.

## 4. Duration budgets per interaction class

### 4.1 What Apple publishes and what it does not

Apple publishes no per interaction duration table. No HIG page says taps take X ms and sheets take Y ms. The numbers below are every explicit duration Apple does publish for the topics in this file, and the honest budget for the pill is to stay inside them rather than invent finer classes.

### 4.2 The published numbers [First party]

Live Activities and widgets cap all animations at two seconds maximum, and the system skips animations entirely on Always On displays with reduced luminance (Sources: https://developer.apple.com/design/human-interface-guidelines/live-activities and https://developer.apple.com/documentation/widgetkit/animating-data-updates-in-widgets-and-live-activities). SwiftUI custom timing curves default to 0.35 seconds (Source: https://developer.apple.com/documentation/swiftui/animation/timingcurve(_:_:_:_:duration:)). Springs and all three presets default to a perceptual duration of 0.5 seconds (Sources: https://developer.apple.com/documentation/swiftui/animation/spring(duration:bounce:blendduration:) and https://developer.apple.com/documentation/swiftui/spring/smooth(duration:extrabounce/)). The HIG contributes qualitative budgets only. Feedback animations should be brief and precise, motion on frequently repeated interactions should generally be avoided, and people must be able to cancel motion rather than wait on it (Source: https://developer.apple.com/design/human-interface-guidelines/motion).

### 4.3 Pill budget derived from the above [Inferred]

Treat 2 seconds as a hard ceiling for any pill animation, 0.5 seconds as the default spring for pill state changes (matching Apple's default preset duration), and 0.35 seconds as the default for simple fades or opacity crossfades. Keep frequently repeated motion (level bars, progress shimmer) free of fixed duration easing entirely by driving it per frame from audio timestamps, per the existing meter ballistics. These mappings are inference; Apple publishes the endpoints, not the pill classes.

## 5. Interruptible and retargetable animations

### 5.1 Springs retarget with velocity preserved [First party]

When a new spring animation starts before the old one finishes, the spring adopts its current velocity as the initial velocity toward the new target, which keeps interruptions smooth and natural (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). SwiftUI tracks gesture velocity automatically, so springs handed off from a gesture continue without extra code (Source: https://developer.apple.com/videos/play/wwdc2023/10158/). Persistent springs (`spring()`, `interactiveSpring()`) replace their successor on the same property while preserving velocity, with an optional blend over `blendDuration` (Source: https://developer.apple.com/documentation/swiftui/animation/spring(duration:bounce:blendduration/)). Interpolating springs instead preserve velocity additively across overlapping animations (Source: https://developer.apple.com/documentation/swiftui/animation/spring(duration:bounce:blendduration/)).

### 5.2 UIViewPropertyAnimator, the UIKit mechanism [First party]

`UIViewPropertyAnimator` exists to make UIKit animations pausable, scrubbable, reversible, and retargetable. It supports start, pause, resume, and stop, adding animation blocks after start, scrubbing a paused animation through `fractionComplete`, reversing through `isReversed`, and re timing a partially complete animation by pausing then calling `continueAnimation(withTimingParameters:durationFactor:)` (Source: https://developer.apple.com/documentation/uikit/uiviewpropertyanimator). `fractionComplete` runs 0.0 to 1.0 and assigning it while paused drives interactive animations such as pan driven transitions (Source: https://developer.apple.com/documentation/uikit/uiviewanimating/fractioncomplete). The animator must declare `isInterruptible` true before `startAnimation()` runs if pause or stop will ever be used, and interruptible animators back interruptible view controller transitions (Source: https://developer.apple.com/documentation/uikit/uiviewpropertyanimator/isinterruptible). Since iOS 8 additive animations are the default for UIKit created animations, so a replacement animation adds onto the in flight presentation value instead of jumping the view to its model endpoint first (Source: https://nonstrict.eu/wwdcindex/wwdc2014/236/).

### 5.3 Continuous gestures and momentum projection [First party]

Apple's gesture rule is to use recognizers that stream continuous information (touches, pan) rather than end of gesture detectors such as swipe recognizers, and to show continuous feedback during the interaction, for example a button that grows with touch pressure to teach that harder pressing completes the action (Source: https://developer.apple.com/videos/play/wwdc2018/803/). For flung objects Apple projects the endpoint from release velocity plus deceleration rate and retargets the spring there, rather than picking the nearest endpoint by position, so a light flick across the screen reaches the far corner the user meant (Source: https://developer.apple.com/videos/play/wwdc2018/803/). The WWDC24 talk shows the modern form. During a drag, each gesture change event creates a new `.interactiveSpring` that retargets the last one, and on release a final non interactive spring carries forward the accumulated velocity with no manual unit velocity math (Source: https://developer.apple.com/videos/play/wwdc2024/10145/). The iOS 18 zoom transition applies the same thinking to navigation. Because transitions can now begin at any time, handlers must call push regardless of transition state and views should be functional so continuous changes flow through (Source: https://developer.apple.com/videos/play/wwdc2024/10145/).

### 5.4 Pill rule [Inferred]

Every pill state change must be retargetable mid flight with velocity preserved: show, hide, listen to transcribing morph, error presentation, and user drag repositioning. Never disable input during a pill animation. Never restart an animation from its model endpoint when the visible frame sits elsewhere. Fixed keyframe sequences are banned for the pill frame for exactly the reason Apple gives: they cannot retarget.

## 6. Dynamic Island expansion mechanics

### 6.1 Three presentations and how the system picks them [First party]

The Island has three size classes called compact, expanded, and minimal (Source: https://developer.apple.com/videos/play/wwdc2023/10194/). With one active Live Activity the system shows the compact presentation, built from leading and trailing elements flanking the TrueDepth camera that must read as one piece through consistent color and type (Source: https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities). With several active activities the system shows two of them in minimal presentation, one attached to the Island and one detached, and an app with several simultaneous activities can set a relevance score to pick which one surfaces (Source: https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities). Touching and holding a compact or minimal presentation opens the expanded presentation, which also appears briefly for important updates (Source: https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities). The expanded layout divides into leading, trailing, center (below the camera), and bottom regions, with an optional priority that grants one region full width (Source: https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities).

### 6.2 Exact published dimensions [First party]

The HIG publishes a size table for two portrait screen classes plus device widths (Source: https://developer.apple.com/design/human-interface-guidelines/live-activities). On a 430x932 screen compact leading and trailing each measure 62.33x36.67 pt, minimal spans 36.67 to 45 pt wide by 36.67 pt tall, expanded spans 408 pt wide by 84 to 160 pt tall, and Lock Screen spans 408 pt wide by 84 to 160 pt tall. On a 393x852 screen compact leading and trailing each measure 52.33x36.67 pt with the same minimal, expanded, and Lock Screen ranges at 371 pt width. The Island corner radius is 44 pt and its rounded shape matches the TrueDepth camera. Compact and minimal width is 250 pt on Max and Plus sized phones and 230 pt on standard sized phones across the iPhone 14 Pro through iPhone 17 lines and iPhone Air; expanded width is 408 pt on the larger phones and 371 pt on the smaller ones. All figures in this paragraph come from that HIG table.

### 6.3 Layout and behavior rules [First party]

Content must sit concentrically inside the pill with even margins, never poking into corners, and expanded layouts must hug the sensor instead of leaving a forehead gap that calls attention to the hardware (Source: https://developer.apple.com/videos/play/wwdc2023/10194/). The Island should feel like a living organism with deliberate elasticity, playful against the fixed hardware, with each activity keeping its own identity inside one family (Source: https://developer.apple.com/videos/play/wwdc2023/10194/). Behavior rules are strict. Tapping an activity must land directly on related detail. Apps must not draw UI that points at the Island or interacts with it. End the activity immediately when the work ends, with at most a short summary linger. Alert (which lights the screen, plays the notification sound, and shows the expanded presentation) only for essential updates, and never pair a Live Activity alert with a push notification for the same update (Source: https://developer.apple.com/design/human-interface-guidelines/live-activities). Prefer one Live Activity that rotates through events over several parallel ones, and offer in app controls plus App Shortcuts so users can start and stop activities without going to Settings (Source: https://developer.apple.com/design/human-interface-guidelines/live-activities).

### 6.4 Content transitions inside Live Activities [First party]

Beyond the extend and contract transitions, Live Activity animations cap at two seconds (Source: https://developer.apple.com/design/human-interface-guidelines/live-activities). Use numeric content transitions for counting numbers and content replace transitions for graphic and text swaps, or build custom transitions from scale, opacity, and position (Source: https://developer.apple.com/videos/play/wwdc2023/10194/). Preserve layout across updates by animating existing elements to their new positions rather than removing and re adding them, and when animating list reorder move only the single relocating row while fading the rest in and out to avoid overlap (Source: https://developer.apple.com/videos/play/wwdc2023/10194/).

## 7. SF Symbols animation

### 7.1 Effect library and meaning [First party]

SF Symbols ships configurable animations that work on every symbol in all rendering modes, weights, and scales, including custom symbols (Source: https://developer.apple.com/design/human-interface-guidelines/sf-symbols). Bounce briefly scales a symbol with an elastic move up or down and back, plays once by default, and signals that an action occurred or needs to occur. Scale changes symbol size and persists until removed, which suits selection focus or press feedback. Pulse varies opacity over time and suits ongoing activity played until a condition clears. Breathe varies opacity and size together for a living quality, which suits status changes or an ongoing recording session (Sources: https://developer.apple.com/design/human-interface-guidelines/sf-symbols and https://developer.apple.com/videos/play/wwdc2024/10188/). The full preset set adds Appear, Disappear, Variable Color, Replace, Wiggle, Rotate, Draw On, and Draw Off plus Magic Replace for continuity between related symbols (Sources: https://developer.apple.com/videos/play/wwdc2023/10197/ and https://developer.apple.com/sf-symbols/).

### 7.2 Discrete versus indefinite behavior [First party]

Each effect declares its behavior. Bounce is discrete: adding it performs one bounce with no removal step needed, and a repeat count option plays it N times (Source: https://developer.apple.com/videos/play/wwdc2023/10258/). Scale is indefinite: it holds its state until explicitly removed (Source: https://developer.apple.com/videos/play/wwdc2023/10258/). Pulse and Variable Color support both modes, playing once when applied discretely or looping until removed when applied indefinitely (Source: https://developer.apple.com/videos/play/wwdc2023/10258/). In SwiftUI the `symbolEffect` modifier propagates down the view hierarchy and `symbolEffectsRemoved` opts a subtree out; AppKit and UIKit use `addSymbolEffect` / `removeSymbolEffect` with an animated flag for applying state without animation (Source: https://developer.apple.com/videos/play/wwdc2023/10258/).

### 7.3 When to use which [First party]

Apple's selection rules map directly onto pill states. Bounce confirms that an action occurred or prompts one, such as hitting maximum brightness at a slider end (Source: https://developer.apple.com/videos/play/wwdc2023/10197/). Scale confirms selection or press, growing momentarily for acknowledgment or shrinking and returning to mimic a physical button (Source: https://developer.apple.com/videos/play/wwdc2023/10197/). Pulse communicates ongoing activity such as screen sharing, optionally pulsing only annotated layers so the signal stays precise (Source: https://developer.apple.com/videos/play/wwdc2023/10197/). Breathe fits an ongoing recording session better than pulse when the icon should feel present and alive rather than merely blinking (Source: https://developer.apple.com/videos/play/wwdc2024/10188/). Apple closes with the restraint rule. Too many symbol animations, or animation in the wrong context, overwhelms and pulls attention from content and actions (Source: https://developer.apple.com/videos/play/wwdc2024/10188/).

## 8. Reduced motion handling

### 8.1 What must change [First party]

The HIG accessibility page requires cutting automatic and repetitive animation including zoom, scale, and peripheral motion when Reduce Motion is active, and replacing meaningful motion with tighter springs, gesture tracked motion, axis fades instead of slides, and no blur animation rather than deleting the signal (Source: https://developer.apple.com/design/human-interface-guidelines/accessibility). App Store review criteria list the triggers explicitly. Disable or change depth simulation (parallax, animated blur, depth of field), multi axis motion, multi speed motion, spinning, and vortex effects, and stop auto advancing carousels or hand the user a stop control (Source: https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria). Decorative animation may stop entirely, but motion that carries meaning such as a status change or a hierarchy transition must be replaced with a dissolve, highlight fade, or color shift (Source: https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria). Motion must also never be the only channel: pair state with color plus text plus sound plus haptics so silenced, glance away, and VoiceOver cases all still read (Source: https://developer.apple.com/design/human-interface-guidelines/feedback).

### 8.2 Detection APIs [First party]

UIKit exposes `UIAccessibility.isReduceMotionEnabled` plus `reduceMotionStatusDidChangeNotification` for runtime changes, alongside `prefersCrossFadeTransitions` which combines Reduce Motion with the Prefer Cross Fade Transitions setting (Sources: https://developer.apple.com/documentation/uikit/uiaccessibility/isreducemotionenabled, https://developer.apple.com/documentation/uikit/uiaccessibility, and https://developer.apple.com/documentation/UIKit/accessibility-for-uikit). SwiftUI reads the same setting through the `accessibilityReduceMotion` environment value. Sampling code observes the notification and branches between full motion and reduced motion effects (Source: https://wwdcnotes.com/documentation/wwdc20-10020-make-your-app-visually-accessible/). The review guidance adds that an in app setting is optional but the system setting must be respected automatically so users never configure motion twice (Source: https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria).

### 8.3 Vestibular numbers [First party]

Two numeric vestibular rules exist. Avoid sustained oscillation, especially near 0.2 Hz, keeping amplitude low and content translucent where oscillation is unavoidable (Source: https://developer.apple.com/design/human-interface-guidelines/motion). Spinning, scaling, and peripheral motion are the named triggers for dizziness and nausea even on 2D screens, so they are the first candidates for gating (Source: https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria).

### 8.4 Web equivalent for the pill [Inferred]

Gate every pill animation on `matchMedia("(prefers-reduced-motion: reduce)")` with a live change listener, freezing the idle drift to a static dot, replacing slide and scale transitions with opacity crossfades under 0.35 seconds, and killing shimmer and oscillation. This mirrors the existing waveform doc pattern and implements Apple's replace don't remove rule. Keep state text always visible so no meaning rides on motion alone.

## 9. ProMotion and 120 Hz considerations

### 9.1 Display behavior [First party]

ProMotion displays switch frame rates dynamically. iPad Pro ranges 24 Hz to 120 Hz and supported iPhones range 10 Hz to 120 Hz (Source: https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays). At 120 Hz the display refreshes every 8 ms against 16 ms at 60 Hz, and the panel adapts to on screen content to save power rather than repeating frames at a fixed cadence (Source: https://developer.apple.com/videos/play/wwdc2021/10147/). Published iPhone steps include 120, 80, 60, 48, 40, 30, 24, 20, 16, 15, 12, and 10 Hz with per step millisecond timings (Source: https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays). The frame rate can drop at any time. The user Limit Frame Rate accessibility toggle caps at 60 Hz, thermal state can restrict 120 Hz, and iPadOS 15 and later enforce the 60 Hz cap in Low Power Mode (Source: https://developer.apple.com/videos/play/wwdc2021/10147/).

### 9.2 What developers must do [First party]

UIKit, SpriteKit, SwiftUI, and `CAAnimation` frame pacing is automatic; custom per frame drawing is not (Source: https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays). Custom drawing must use `CADisplayLink` (or `CVDisplayLink` on macOS) rather than `NSTimer`, which drifts out of phase and drops frames, and must follow four practices: query the refresh rate at runtime instead of hard coding it, use the display link's own rate, sample progress at `targetTimestamp` (the coming vsync deadline) rather than `timestamp`, and compute time deltas dynamically so mid flight rate changes stay smooth (Source: https://developer.apple.com/videos/play/wwdc2021/10147/). Apps declare their needs through `preferredFrameRateRange` (minimum, maximum, preferred); iPhone apps must also set the `CADisableMinimumFrameDurationOnPhone` plist key to true or Core Animation never exceeds 60 Hz (Source: https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays). Apple reserves one explicit range. High impact animations such as grid to fullscreen expansion, sheet presentation, or full motion gaming may request `CAFrameRateRange(minimum: 80, maximum: 120, preferred: 120)` but should use it sparingly for power (Source: https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays). Never assume the callback arrives at the requested rate (Source: https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays).

### 9.3 Web equivalent for the pill [Inferred]

Drive the pill meter with `requestAnimationFrame` timestamps and integrate smoothing against elapsed delta time, never against frame counts, so 60, 120, and 144 Hz displays behave alike. Keep per frame canvas work allocation free and compositor only (transform plus opacity) for DOM motion. Treat high refresh as a readability win for the attack follower, not a reason to add motion.

## 10. Steal list for the 364x64 pill

Constraints. One fixed frame, two accents only. Teal means working, coral means failed. Everything else stays neutral.

1. Default spring for all pill state changes: duration 0.5, bounce 0. [First party] numbers from the smooth preset (Sources: https://developer.apple.com/documentation/swiftui/spring/smooth(duration:extrabounce/) and https://developer.apple.com/videos/play/wwdc2023/10158/). [Inferred] web form: drive with a JS spring solver at those parameters, not a fixed Bezier, so retargets preserve velocity.
2. Snappy variant for gesture release and confirmation pops: duration 0.4 to 0.5, bounce 0.15. [First party] base values (Source: https://developer.apple.com/documentation/swiftui/spring/snappy(duration:extrabounce/)). [Inferred] reserve for the push to talk release and the done confirmation. [First party] mechanism: velocity preserving springs plus additive replacement (Sources: https://developer.apple.com/videos/play/wwdc2023/10158/ and https://nonstrict.eu/wwdcindex/wwdc2014/236/). [Inferred] pill form: breathe style opacity plus size drift on the listening glyph, single discrete pop on injection done, persistent highlight while selected or hovered, and no more than one animated status element at a time.

## 11. Non goals

Per class duration tables. Apple does not publish them, so inventing tap versus sheet millisecond budgets would be fabrication. The pill uses the section 4 endpoints only.

Exact Apple spring vibration in the pill. The conversion equations are exact, but mass 1 plus computed stiffness and damping describe Apple's curve shapes, not a mandate to feel identical on a Linux desktop with different input latency and refresh behavior. Match the parameters, not an imagined feel.

Dynamic Island cloning. Compact, minimal, and expanded presentations solve phone multitasking across timers, calls, scores, and rides. The pill tracks one dictation session. Copy the layout discipline and the expansion coherence, not the three presentations.

SF Symbols assets. The effects library is OS bound. Copy the meaning map (bounce confirms, pulse continues, breathe records), not the artwork.

ProMotion frame pinning. The web pill must adapt to whatever cadence the compositor gives, including 60 Hz caps from power saving, exactly as Apple requires native apps to adapt. Never assume 120 Hz.

Parallax, blur animation, spin, and sustained oscillation. These are the exact vestibular triggers Apple names, including the 0.2 Hz caution (Sources: https://developer.apple.com/design/human-interface-guidelines/motion and https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria). None belong in the pill under any motion setting.
